# GentleSight

**Live Demo:** [gentlesight-demo.vercel.app](https://gentlesight-demo.vercel.app)

GentleSight is an interactive Next.js prototype that explains how NILM-style home energy signals can be interpreted as daily living routines and summarized for a guardian-facing app.

The demo uses local mock data and a rule-based NILM engine. It does not connect to a live sensor backend or database. When `OPENAI_API_KEY` is configured, the guardian report copy is generated by OpenAI; otherwise a local fallback is used.

## Overview

GentleSight presents a realistic home scene where simulated time flows on its own. The app compares the current day against a mock 28-day personal baseline across six living-routine windows (morning wake, breakfast, late-morning rest, noon activity, evening routine, pre-sleep stability) and summarizes only living-rhythm changes for a guardian-facing UI.

The prototype focuses on:

- Autonomous day simulation with reset, pause, and fast preview controls
- Appliance interaction over a realistic home image
- Full-day personal baseline comparison across six routine windows
- Holistic change score that reflects all baseline windows observed so far, not just the current one
- Unresolved caution prioritization: the guardian message always surfaces the most critical unresolved window
- Role-specific Guardian reports for family guardians (warm tone) and social workers (professional tone)
- Privacy-safe living-rhythm panels instead of raw appliance logs
- An educational explainer showing how user-created demo inputs are transformed into safer summaries

## Features

- Interactive home view with appliance touch targets
- Autonomous simulated time starting at 07:30 with fast-preview mode
- Guardian panel with `Guardian`, `상태`, `기준선`, `프라이버시` tabs (landscape mobile overlay)
- Guardian phone panel on desktop with role selection and bilingual report copy (Korean / English)
- Holistic change score (0–95) weighted across all elapsed baseline windows for the day
- Unresolved caution stack: when multiple windows are missed, the most recent caution is shown in the report with a count of earlier unresolved items
- Privacy summary panel with explicit confirmation before raw-processing logs are revealed
- OpenAI-backed report message, supporting suggestion, and change summary when `OPENAI_API_KEY` is set
- Privacy-safe AI payload: raw appliance fields and clock-like values are blocked before the API call

## Living Routine Baseline

The mock baseline covers six windows derived from a 28-day personal history:

| ID | Phase | Typical window | Signal |
| --- | --- | --- | --- |
| `morning-start` | Morning | 07:50–08:20 | Wake |
| `breakfast` | Morning | 08:00–08:40 | Meal |
| `late-morning-rest` | Morning | 09:00–11:00 | Rest |
| `noon` | Noon | 11:30–12:30 | Any |
| `evening` | Evening | 18:30–20:00 | Any |
| `night` | Night | 21:30–22:30 | Rest |

Each window has an observe-after time and a caution-after time. The rule engine promotes a window from scheduled → in-progress → watch → caution or confirmed as the day advances.

## Holistic Change Score

The change score (shown as **변화도** for family or **우선도** for social workers) reflects all elapsed baseline windows for the current day, not just the active one:

- A missed caution window contributes a score of 60–95 (weight ×3)
- A late-confirmed window contributes 35–62 (weight ×2)
- An on-time confirmed window contributes 5–27 (weight ×1)

The final score is a blend of the weighted average (60%) and the single highest window score (40%), so one serious missed window elevates the score even when the current window is stable.

## Privacy Model

The default guardian UI does not send raw appliance events to the AI report endpoint. The API rejects raw event fields such as `events`, `appliance`, `applianceLabel`, `powerDelta`, `duration`, `waveform`, `time`, and `baselineTime`. Clock-like raw values (e.g. `07:50`) and appliance brand names are also blocked in report summary text.

For prototype explanation, the privacy panel can reveal raw processing logs only after explicit confirmation. This is intended to show how user-created demo inputs are transformed into safer summaries:

```text
Raw demo input → De-identified living-rhythm signal → AI-safe report input
```

## AI API Contract

`POST /api/report` validates a privacy-safe report payload and generates the guardian report copy through OpenAI when `OPENAI_API_KEY` is configured. Without a key, or if the provider response is unsafe or malformed, the endpoint returns a local fallback so the demo remains fully usable.

Expected payload:

```json
{
  "routineState": "아침 루틴 지연",
  "confidence": 91,
  "severity": "caution",
  "changeLevel": "clear_change",
  "role": "family",
  "language": "ko",
  "riskScore": 84,
  "baselineComparison": "평소 생활 리듬 범위에서 뚜렷하게 벗어남",
  "reasonSummary": "오전 활동 시작이 기준선보다 늦음",
  "trendSummary": "확인 필요",
  "recommendedAction": "전화하기",
  "privacyPolicyMarker": "PRIVACY_SAFE_SUMMARY_ONLY"
}
```

`changeLevel` is one of `stable | watch | clear_change` and is derived from `severity` and `lateConfirmed` by the client before the request is sent. Raw fields are blocked even when nested inside another object. Clock-like raw values such as `07:50` are also rejected in report summaries.

Expected response:

```json
{
  "message": "오늘 아침 생활 리듬이 평소보다 늦어 보여요. 가볍게 안부를 확인해보세요.",
  "supportingSuggestion": "통화가 어렵다면 짧은 메시지를 남겨보세요.",
  "changeSummary": "평소보다 뚜렷한 아침 리듬 변화가 요약되었습니다.",
  "source": "openai",
  "model": "gpt-5.4-mini"
}
```

The AI generates only the three guardian-facing copy fields: `message`, `supportingSuggestion`, and `changeSummary`. Title, severity, tone, CTA, change score, and notification badges remain rule-based. The response is validated against a strict JSON schema before it is used. Configure `OPENAI_REPORT_MODEL` to override the default `gpt-5.4-mini` model.

Role-specific prompt instructions are injected automatically: the `family` role receives a warm, personal tone; the `socialWorker` role receives a professional, clinical tone focused on behavioral deviations and case-management implications.
